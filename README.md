# memory-chain

> 把 AI 会话压缩成结构化交接笔记，按**事件链**归档；新会话读回即可接着干。
> 一个纯文件方案：不依赖插件、不依赖数据库、不依赖向量检索。

版本 **v1.5** · MIT · 一作 / 实现：**鲸跃** · 上传与验收：**Fatcat515**

---

## 它解决什么问题

LLM 会话的上下文会满。满了就得开新会话，于是：

- 上一轮谈定的方案没了；
- 做到一半的活不知道做到哪；
- 踩过的坑再踩一遍。

已有的解法各有代价：全量塞回去烧钱且降智；向量检索把「结论」和「过程」混着召回；
自动摘要看起来都对，但**每条都不带出处**——三个月后读到，只能选择相信或不信，而两条路都不对。

memory-chain 的做法是：**把上下文扔掉，只留结论，并且给它一个能查回去的地址。**

---

## 四个核心约定

**1. 一条事件链 = 一个目录**

```
$DSH_HOME/handoff/<工作区slug>/
    2026-10-23_handoff-system/          ← 一条叙事链
        2026-10-23_2305_handoff-layout_1e40c09a.md
        2026-10-23_2338_chain-dirs_1e40c09a.md
    2026-10-21_stellaris-mod/            ← 另一条链，互不干扰
    legacy-2026-10-23.md                 ← 未归链的旧账
```

**2. 一次交接 = 一个文件，只增不改**

命名 `YYYY-MM-DD_HHMM_<主题>_<会话id前8>.md`。时间前缀保证「文件名排序 = 时间排序」，
所以「取最新」只要取文件名最大的那个——不需要读 mtime（批量改名会把 mtime 全刷成同一时刻）。

多个会话并行写入时**零冲突**：各写各的文件，谁也不用等谁。

**3. 链条靠指针串，不靠把历史抄一遍**

每份笔记顶部有一行 `继承自`：同链内写链名，跨链写 `<链名>/<文件名>`，混合继承用 ` + ` 连。
新笔记只写「仍然有效的前提」+「这次的新进展」，不复述上一条的全过程。

**4. 通道分三类：链 / 散条 / 便条**

| 通道 | 放哪 | 寿命 | 参与「接上次」 |
|---|---|---|---|
| **链**（叙事） | `<链目录>/` | 永久、只追加 | ✅ |
| **散条**（轻量结论） | 工作区根 | 中等，等长大 | ❌ |
| **便条**（传话 / 派活） | 工作区根，文件名带 `_memo_` | 短，处理完删 | ❌ |

一句话：**产生结论 → 进链；只是传递动作 → 进便条。**

便条是给「另一个会话」派活用的。流程是：写清收件人 → 对方处理完**追加一行签收**（绝不重写整个文件，否则并发会互相覆盖）→
**最后一个签收人负责删除**。删除的硬前提是：**处理结果已经写进链**——便条可以不留，历史必须留。

## 安装

把整个 `memory-chain/` 目录复制到：

```
%USERPROFILE%\.agents\skills\memory-chain\
```

**不需要重启**，技能是纯文件读取，复制完即可用。

### 可选：让它自动生效

把 `AGENTS.md.example` 复制成 `%USERPROFILE%\.dsh\AGENTS.md`（每轮自动注入，约 1KB）。
这样每个新会话开局就知道有这么个机制、什么时候该用，不用你先说触发词。

## 用法

| 你说 | 它做什么 |
|---|---|
| 「交接一下」/「准备交接文件」 | **正式**：写完整六段笔记，归属到某条链 |
| 「压缩一下」/「记一下」/「存个档」 | **轻量**：写三五行散条，不建链 |
| 「接上次」/「读交接笔记」 | 读链目录里文件名最大的那份，复述目标、进度、下一步 |
| 「@某段旧会话，继承过来」 | 直读会话原始记录，筛出真人输入再压缩（模式三） |
| 「让 X 去做 Y」/「给某条链传话」 | **便条**：写进工作区根（`_memo_` 前缀），可签收、可删除、不进链 |
| 「之前那个 X 怎么弄的」/「找一下 X」 | **检索**：先扫链索引，再扫正文兜底，返回**一条时间线**而不是一份文件（模式四） |

正式笔记的六段：**任务目标 / 当前进度 / 关键决策 / 涉及文件 / 下一步 / 坑与禁忌**。

两个容易被忽略的字段：

- **涉及文件**必须写**绝对路径**。「在桌面上有个快捷方式」这种写法，下一个人会把桌面翻一遍还是找不到。
- **下一步**每条带来源标记：`[新]` 是本轮产生的，`[遗留·MM-DD起]` 是上次就挂着、至今没结的，并补一句「卡在…」。不标来源，几轮之后会攒成一堆不知道什么年代的僵尸待办。

## 链索引与检索

链一旦变多，「接上次」只解决**最新一份**，翻旧账就没有路径了。v1.2 加了索引层：

```
L0  常驻      AGENTS.md 的触发词
L1  索引      <链目录>/INDEX.md      一行一条，只指路不承载结论   ← v1.2 新增
L2  记录      单份交接
L3  原料      会话原始记录（read-session）
```

**索引长这样**（固定格式，检索靠它识别）：

```markdown
- `2130` · 推荐流必然失败，改一行修掉 · `#抖音` `#推荐流` `#video.id`
- `2038` · purge 结案，73/73 补丁全打上 · `#purge` `#结案` `#补丁` ✅结论
```

**检索走三层，命中即停**：

| 层 | 做什么 | 代价 |
|---|---|---|
| 1 | 扫所有 `INDEX.md` | 几十行，最快 |
| 2 | 全文扫描，**只报命中次数不打印正文** | 慢但全，兜住索引漏更新 |
| 3 | 读选定那份 | 按需 |

**v1.3：补记不再另开文件**

一件事的补充，用 `amend` 并进**最新那份**，不新开一份：

```bash
node mem.mjs amend --chain <链> [--to <记录名片段>] --title "<小节标题>" --text "<正文>"
```

- 文件里多一节「## 补记 · 小节标题（HH:MM）」，历史内容一个字不动
- INDEX 对应行标「+补记」（第二次「+补记2」），一眼看出这份被补过几次
- 判断口径：**一件事的补充 → amend；新的一件事 → append**

这条来自一个真实教训：此前的规范把记录分成「轻量散条 / 正式交接」两层，
实测一个多月，散条层**从未被使用** —— 本该轻的东西全写成了链，
结果是「每件小事一份交接」（两天 8 份）。**频率靠合并控制，不靠分层。**

**v1.4：写之前先看旧的**

`append` 只会往后加，不看前面 —— 同一条链里因此出现过两份互相矛盾的结论，
后来读的人（包括下一个自己）分不清哪条算数。v1.4 加了三个东西：

- `probe --chain <链> <关键词…>` —— 只查不改，把同主题的旧结论/旧记录先摆出来
- `consolidate --chain <链>` —— 生成/刷新该链的结论层 `DECISIONS.md`，只抽「关键决策」段，不编内容
- 写锁：`.consolidate.lock`，活锁跳过、死锁接管（10 分钟 TTL）

判断口径：命中旧结论且仍生效 → 这次是修正，用 `amend`；是新进展 → `append`。

**v1.5：住户的人格，和便条的到期**

两条规矩补进技能本体：

- **住户的人格（自建、自维护）** —— 每个有名住户可以建立并自行维护自己的人格卡，
  不必等谁代写；但「谁的人格谁写，别人只提议、不落笔」。人格是「我是谁」，链是「我经历过什么」。
- **便条的到期与收口（发件人负责）** —— 便条头部必须写 `**到期**`；
  到期无人签收 → 摘要写进链 → 文件移进 `_memo_archive/`。
  收口责任在**发件人**，不在收件人：异侧收件人（没有文件权限、没有签收时机）永远签不了。

这条同样是实测出来的：本机曾积压 10 份零签收的便条（10-26 ~ 11-18）。
早期能正常闭环的两份，收件人都是「自己这一侧」——所以问题不是收件人懒，是机制缺了收口这一环。

**三条设计原则**：

- **只追加不改写** —— 和链记录同一原则。结论变了就追加新行，`✅结论` 标记挪过去，旧行原样留着。
- **只指路不承载结论** —— 写「这件事是什么」，不写「结论是否正确」。索引里的结论会腐烂，原文不会。
- **索引是快速通道，不是唯一入口** —— 漏更新不至于丢东西，只是慢一次。

**关键词打"你想怎么搜"，不是"你想怎么写"**。实测：一份叫「两条尾巴的处理决定」的记录，正文全是 purge / node，标题里一个都没有——不标关键词就搜不到。

## 身份：住户与门牌

便条要能送到，得先分得清"给谁"。这里有两类身份，别混：

| | **住户**（有名会话） | **门牌**（链 / 工位） |
|---|---|---|
| 例子 | 鲸跃、鲸渡 | 做标书、写周报 |
| 怎么识别 | 链里写着「本链会话自称 X」，新会话读到就继承这个身份 | 目录名 / 链名 |
| 能跨链被找到 | ✅ 便条写名字就行 | ❌ 只在这条链内有效 |
| 维护成本 | 要维护 | 零 |

**该不该给会话起名，一条判据**：这个角色会不会**被反复调用、跨链协调、长期存在**？

- 会 → 起名，并在链里记一行 `本链会话自称：<名字>`
- 不会 → **不起名**。它的身份就是那条链的名字，做完归档

★ 给一次性的活起名字是给自己找维护成本——下个会话读到「本链自称小报」还得判断"我是不是小报"。

## 工具：read-session

`tools/read-session.mjs` 用来直读 DSH 会话原始记录（多帧 zstd 压缩的 jsonl），
**零第三方依赖**（只用 `node:fs` / `node:path` / `node:zlib`）。

```bash
read-session.cmd list                    # 列出本机会话：id / 大小 / 时间 / cwd / 文件路径
read-session.cmd dump <file> --out o.txt # 解压并按来源分类，输出六段报告
read-session.cmd schema                  # 列出全部记录类型的字段结构
```

`.cmd` 是 Windows 包装器（自动找 node：先 PATH，再用 DSH 自带 runtime）。其他平台直接 `node read-session.mjs`。

**为什么需要它**：`@` 引用的会话快照只有 `role + text`，没有工具调用。
实测一段 2137 条事件的旧会话里，65 条 `user/message` 中有 **32 条（49%）是系统注入**——
时间戳、运行时上下文、技能目录变更、后台任务通知。它们被当成"用户消息"存着，**但不是用户说的话**。
对着快照做压缩，就会把系统注入当成用户的决定记下来。

按 `data.source.kind === "user"` 这个结构化判据筛，才能只拿到真人输入。

## ⚠️ 隐私与数据范围

**这个工具会读取本机 DSH 会话的原始记录**：

```
$DSH_HOME/sessions/<工作区目录名>/<会话id>/session.v4.jsonl.zstd
```

这些文件包含**完整的历史对话原文**——用户输入、模型回复、工具调用与结果。

使用前请确认：

- 这些会话是**你自己的**；
- 若在共享机器上，不要对他人会话使用；
- 默认行为是**只读用户点名的那一段会话**，不主动遍历或窥探；
- 压缩生成的交接笔记是**明文 markdown**，落在 `$DSH_HOME/handoff/` 下，**不加密**。
  凭据、密钥、客户隐私不要写进笔记——真要记，写「密钥在 X 处」而不是密钥本身。

## 已知限制

- **不自动触发**。技能按需加载，得有人说一句，或由 agent 主动建议。
  想全自动（上下文快满时自己落盘）需要监听 token 用量，那得写插件，不在本项目的范围。
- **压缩是转述，不是原文**。所以流程里有一条红线：写完必须让用户扫一眼要点，那是唯一的失真兜底。
- **文件策略收紧时**（DSH 的 `workspace-write`），`~/.dsh` 在工作区外，写入会被沙箱拒绝。
  SKILL.md 里内置了三级回退：`DSH_HANDOFF_DIR` → `$DSH_HOME/handoff` → `<工作区>/.handoff`。
- 会话存储格式是 `session.v4`。上游若改格式，`read-session` 需要跟着改（脚本内已有正则兜底判据）。
